# TrackBus v0.2.1 event stability

TrackBus v0.2.1 keeps the v0.2 detector, fusion, and single-ByteTrack pipeline
unchanged. It makes crossing decisions more conservative and makes camera-zone
calibration reproducible. The change addresses a real failure in
`bus_door_02.mp4`, where one unstable box with tracking ID 39 emitted `IN`,
`OUT`, then `IN` at frames 354, 372, and 380.

The [pre-change audit](v0.2.1-event-stability-audit.md) records every baseline
event match, false positive, false negative, track ID, and the reproduced zone
history. The important finding was that the box centre remained inside while
its bottom edge oscillated across the calibrated zones. The v0.2 counter then
accepted three opposite-zone observations without requiring a neutral
traversal or a post-event re-arm.

## Stable crossing state machine

Each tracking ID now follows this sequence:

```text
unknown
  -> stable origin dwell
  -> observed neutral transition
  -> stable destination confirmation
  -> emit one event and latch destination
  -> stable destination dwell before a possible reverse traversal
```

An initial zone establishes the origin and never creates an event. A direct
`OUTSIDE -> INSIDE` or `INSIDE -> OUTSIDE` observation is rejected when no
neutral sample was observed. Returning to the origin cancels a pending
crossing. A short detection gap preserves an otherwise coherent transition; a
gap longer than the configured maximum invalidates uncertain dwell and pending
confirmation. The cooldown is a secondary guard: a valid reverse transition
may remain pending during cooldown, but it still needs origin dwell, neutral
traversal, and destination confirmation.

The backward-compatible `minimum_zone_frames` value remains the fallback for
both dwell settings. The explicit v0.2.1 settings and safe defaults are:

```yaml
tracking:
  minimum_zone_frames: 3
  minimum_origin_zone_frames: 3
  minimum_destination_zone_frames: 3
  maximum_transition_gap_frames: 15
  event_cooldown_frames: 30
  zone_anchor: bottom_center
  zone_boundary_hysteresis: 0.0
```

`zone_anchor` accepts `center`, `bottom_center`, or `top_center`. The default is
the prior bottom-centre behavior. Hysteresis is a normalized inward margin on
each zone polygon; a raw hit too close to an edge becomes a neutral transition
observation. Raw and effective zones are both retained for diagnostics.

These settings are camera calibration parameters, not detector training and
not universal accuracy defaults. Do not weaken them merely to make aggregate
counts match expected totals.

## Diagnostics

With `diagnostics.export_detection_csv: true`, the tracks CSV now records the
selected anchor, raw zone, effective zone, latched stable zone, state-machine
state, pending direction, dwell and confirmation counters, cooldown remaining,
detection gap, suppression reasons, and emitted event. Suppression reasons
include cooldown, insufficient dwell or confirmation, missing neutral
traversal, boundary jitter, and excessive gap.

The run summary records the selected anchor, hysteresis, stability settings,
and aggregate suppression-reason observation counts. These counts describe
diagnostic observations, not a count of distinct rejected events. Doorway
overlap metrics are available only
when a doorway lane or `camera.crossing_corridor` is configured. Otherwise the
summary stores `null` values with an explicit unavailable reason; it no longer
reports a misleading successful zero.

## Camera calibration

Use the model-free editor in a graphical desktop session:

```powershell
python -m trackbus.calibrate_camera `
  --input data/input/bus_door_02.mp4 `
  --output-config configs/cameras/bus_door_02.yaml `
  --frame 350
```

It edits normalized INSIDE, OUTSIDE, optional crossing-corridor, and exclusion
polygons while preserving unrelated YAML settings. It also previews the three
anchor modes and validates polygon area, overlap, neutral space, and corridor
coverage. It refuses exclusions that overlap either counting zone or the
crossing corridor. It does not inspect or infer ground-truth events. See the
[camera-calibration guide](camera-calibration.md) for exact controls.

## Precision configuration

Use `model.precision: fp32` or `model.precision: fp16`. FP32 is the safe default.
The deprecated `model.half` key still loads with one startup migration warning;
it is never forwarded once per frame. With pinned Ultralytics 8.4.95, TrackBus
uses the supported `quantize: 16` prediction option only for FP16 on a validated
CUDA device. It does not enable INT8 quantization or replace PyTorch/CUDA. An
FP16 request on CPU is downgraded once to FP32 with one warning.

## Reproducible evaluation

The bounded matrices each contain the same eight meaningful configurations:
minimal stability reference, safe defaults, longer origin dwell, longer
destination confirmation, longer cooldown, boundary hysteresis, centre anchor,
and top-centre anchor. Detector, fusion, ByteTrack, and full-frame view settings
remain fixed within each video.

```powershell
python -m trackbus.experiments `
  --input data/input/test_video.mp4 `
  --ground-truth data/ground_truth/test_video.events.json `
  --matrix configs/experiments/event_stability_test_video.yaml `
  --output-dir data/experiments/v021_event_stability_test_video

python -m trackbus.experiments `
  --input data/input/bus_door_02.mp4 `
  --ground-truth data/ground_truth/bus_door_02.events.json `
  --matrix configs/experiments/event_stability_bus_door_02.yaml `
  --output-dir data/experiments/v021_event_stability_bus_door_02
```

Ranking uses direction-aware event F1, false positives, recall, aggregate
direction error, rapid same-track event and ID instability, then FPS. A correct
aggregate total alone is never treated as proof of accuracy.

## Final results

Both final matrices completed on CUDA with frame-level ground truth and a
15-frame tolerance. The selected stability values are origin dwell 3,
destination confirmation 3, maximum transition gap 15, cooldown 30, and no
boundary hysteresis. Anchor is calibrated per camera: bottom-centre for
`test_video` and centre for `bus_door_02`.

| Video | Configuration | IN / OUT | TP | FP | FN | Precision | Recall | F1 | FPS |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| test_video | v0.2 baseline | 3 / 2 | 5 | 0 | 3 | 1.000 | 0.625 | 0.769 | ~24 historical |
| test_video | v0.2.1 selected | 3 / 2 | 5 | 0 | 3 | 1.000 | 0.625 | 0.769 | 24.94 |
| bus_door_02 | v0.2 baseline | 4 / 1 | 1 | 4 | 5 | 0.200 | 0.167 | 0.182 | 17.16 historical |
| bus_door_02 | v0.2.1 selected | 4 / 0 | 3 | 1 | 3 | 0.750 | 0.500 | 0.600 | 8.77 |

The selected test-video events remain OUT at frames 94 (ID 3) and 132 (ID 8),
plus IN at 209 (ID 18), 257 (ID 30), and 294 (ID 33). Thus v0.2.1 does not
materially regress the required 0.7692 baseline F1.

The selected bus events are IN at frames 415 (ID 68), 510 (ID 76), 640
(ID 147), and 666 (ID 153). Frames 415, 640, and 666 match ground truth at
-9, -4, and -15 frames; frame 510 is the remaining false positive. Ground-truth
frames 330, 364, and 534 remain false negatives. Tracking ID 39 emits no event
with the calibrated centre anchor, so its former `IN -> OUT -> IN` sequence is
fully removed. Correctly matched IN events increase from one to three; no OUT
event remains.

The selected bus summary reports four possible ID-restart warnings. This cannot
be compared as a regression against the old numeric zero: the old camera had no
lane/corridor calibration, so restart matching was unavailable but was
misleadingly serialized as zero. The new corridor makes the diagnostic active.

The 44.66 FPS outlier and broad 7.15-10.55 bus range demonstrate host power,
thermal, and scheduling variation; they are not plausible state-machine speed
effects. A separate selected-settings bus control with the corridor disabled
ran at 9.12 FPS, close to the 8.77 FPS corridor result, so corridor diagnostics
are not the cause of the historical-to-current throughput difference. Within
the same matrix, event logic changes leave detector counts, fused detections,
IDs, and empty frames identical. The historical 17.16 FPS could not be
reproduced under the current laptop state and is retained as a transparent
environmental limitation rather than hidden.

The final test matrix used `device: auto`, which selected CUDA in this
environment, while the historical approximately 24 FPS test-video observation
was reported on CPU. Those equal-looking rates are not a device comparison.

The centre anchor genuinely helps `bus_door_02`, but materially harms
`test_video`; this is why it is stored only in that camera's YAML. Neither
hysteresis nor longer dwell is a universal improvement. The experiment supports
per-camera calibration, not a global centre-anchor rule.

## Limitations

The counter cannot recover a missed detection, repair a fragmented identity, or
split a detector box that covers two people. Anchor calibration can reduce box
geometry sensitivity, but one low-resolution video and one camera view are not
representative validation. The remaining missed events and large/merged boxes
are evidence that a responsibly collected, licensed overhead head or upper-body
dataset and a custom detector are likely the next useful model step.
