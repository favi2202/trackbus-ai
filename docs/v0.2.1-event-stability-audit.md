# TrackBus v0.2.1 event-stability audit

This audit was completed on
`feature/trackbus-v0.2.1-event-stability` before changing counting behavior.
The branch starts at v0.2 commit
`a766018cc56dcc0d6265d3d6042e8f97b4c855bb`. All 158 existing tests passed.

The local `configs/cameras/bus_door_02.yaml` was an untracked, user-owned file.
Its initial SHA-256 was
`cc86746a97c726057c414d9de4b1f38f11381347f95b233aa4175936f04cd468`.
The unrelated untracked `requirements-before-cuda.txt`, ignored videos, model
weights, generated outputs, and virtual environment were not modified or
staged during the audit.

## Reproduction method

Existing prediction artifacts were evaluated direction-aware and one-to-one at
a tolerance of 15 frames:

```powershell
python -m trackbus.evaluation --ground-truth data/ground_truth/test_video.events.json --predictions data/output/result.events.csv --tolerance-frames 15
python -m trackbus.evaluation --ground-truth data/ground_truth/bus_door_02.events.json --predictions data/output/bus_door_02_calibrated_v3.events.csv --tolerance-frames 15
```

Fresh pre-change processing runs used separate `event_stability_pre_*` artifact
names under the ignored `data/output/` directory. The bus run enabled the
existing raw, fused, and tracked CSV exports so no prior output was overwritten.
It reproduced the same five event frames and IDs as the calibrated v3 run.

## Why track 39 emitted IN, OUT, IN

The original v3 output did not include a tracks CSV. A fresh pre-change run
reproduced track 39 and recorded this raw bottom-centre zone sequence:

- frames 330-345: OUTSIDE;
- frames 346-348: neutral transition;
- frames 349-350: INSIDE, frame 351 neutral, frames 352-354 INSIDE;
- frame 354: the third destination observation emits IN;
- frames 355-360: INSIDE mixed with brief neutral classifications;
- frames 361-369: mostly neutral, with one INSIDE observation at 365;
- frames 370-376: OUTSIDE; frame 372 emits OUT after three observations;
- frame 377: no tracked observation;
- frames 378-383: INSIDE; frame 380 emits IN after three observations.

The box was exceptionally unstable: it was about 550-638 pixels tall over this
interval, while its centre remained inside during the entire false reversal.
The saved summary records 93 unusually-wide observations, marks it as a possible
merged detection, and records 58 source-edge touches. This supports the observed
bottom-edge movement being box geometry rather than a genuine passenger exit.

The v0.2 counter made the sequence possible because it:

1. treated the fixed bottom-centre box point as the counting anchor;
2. emitted after three opposite-zone observations;
3. did not require a neutral observation as part of a completed transition;
4. immediately replaced the stable zone after every event;
5. had no post-event latch, reverse re-arming rule, or cooldown; and
6. did not invalidate destination candidates after a bounded source-frame gap.

Thus every three-observation reversal became a new event. The direct
OUTSIDE-to-INSIDE change across missing frame 377 was sufficient for the second
IN even though no reverse neutral traversal was observed.

## Misleading doorway diagnostic zeros

The camera file defines INSIDE and OUTSIDE counting zones but no
`camera.doorway_lanes`. v0.2 defines a doorway person only as a track assigned to
one of those optional lanes. Consequently `maximum_people_in_doorway`, overlap,
and nearby-at-crossing fields were written as numeric zero even though the
measurement was unavailable. Track 39's lane fields are all empty for the same
reason.

v0.2.1 must either use a valid crossing corridor or mark those metrics as
unavailable. A zero must only mean an enabled doorway diagnostic observed zero.

## FP16 warning trace

Ultralytics 8.4.95 maps the deprecated `half` prediction argument to
`quantize=16` and warns every time the argument reaches `YOLO.predict`. TrackBus
already omits `half` when `model.half: false`, and neither fresh reproduction
emitted the warning. The reported spam therefore came from an FP16/older call
path, not the preserved `half: false` camera file. v0.2.1 should resolve
precision once at startup, omit both options for FP32, and use the pinned API's
FP16 form only on validated CUDA.
