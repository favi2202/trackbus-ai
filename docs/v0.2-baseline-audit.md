## v0.1.2 processing architecture

The v0.1.2 runtime is a single sequential loop:

```text
source frame
  -> optional one detection ROI crop
  -> PersonDetector.infer_with_tracking()
  -> YOLO.track(..., persist=True, tracker=ByteTrack YAML)
  -> ROI-local tracked boxes
  -> source-coordinate translation and clipping
  -> exclusion filtering on tracked bottom-center anchors
  -> zone/lane classification and diagnostics
  -> PassengerCounter state machine
  -> annotation, event CSV, and summary JSON
```

Responsibilities before the refactor were:

- `detector.py`: load a standard Ultralytics model and invoke the combined
  detection/tracking API for class 0 (`person`).
- `tracker.py`: convert Ultralytics result boxes and IDs into model-independent
  `TrackedPerson` objects; it did not own a tracker instance itself.
- `calibration.py`: create the optional ROI, translate tracked boxes into the
  source frame, clip boxes, classify lanes, and test exclusion polygons.
- `counter.py`: retain stable OUTSIDE/INSIDE history by temporary track ID and
  emit only complete OUTSIDE -> INSIDE or INSIDE -> OUTSIDE transitions.
- `diagnostics.py`: observe gaps, overlaps, lanes, border contact, likely static
  tracks, and possible ID restarts without changing counts.
- `video_processor.py`: decode and encode video and coordinate every stage.
- `event_logger.py`: stream confirmed events to CSV and write the final JSON
  summary.
- `config.py` / `main.py`: validate YAML and CLI settings and assemble runtime
  components.

The counter already has the required safeguard: the first stable zone only
establishes origin state. UNKNOWN -> INSIDE and UNKNOWN -> OUTSIDE never emit an
event, and this behavior must remain unchanged in v0.2.

## Reproducible full-frame reference

The preserved reference artifact `data/output/v012_diagnostic.summary.json`
reports the 589-frame, 320x240, 25 FPS test video at:

- model `yolo11n.pt`, confidence `0.35`, image size `640`, CPU;
- entered `3`, exited `2`;
- 250 tracked person observations in 185 frames;
- 15 unique tracking IDs;
- 24.43 processing FPS.

The equivalent v0.1.2 command is:

```powershell
python -m trackbus.main --input data/input/test_video.mp4 --config configs/default.yaml --device cpu --model yolo11n.pt --confidence 0.35 --imgsz 640 --output data/output/v012_reproduction.mp4
```

The v0.2 default must retain one full-frame inference view so the same command
shape remains valid. A post-refactor result may differ slightly because the
combined `YOLO.track` call is replaced by explicit `YOLO.predict` plus a wrapped
ByteTrack update; the experiment report must disclose and measure any difference.

## Architectural risks found

`YOLO.track(..., persist=True)` couples prediction and tracker state. It cannot
safely accept detections from several independently cropped views, and creating
one persistent tracker per crop would create unrelated ID spaces. Exclusions are
also applied after tracking in v0.1.2, allowing a static false positive to consume
tracker state even when it is later ignored.

The old ROI experiment cropped inference to `[0.03, 0.30, 0.97, 1.00]`. A sole
crop changes the pixels and spatial history available to the combined detector
and tracker. Tracks entering from the omitted upper portion can first appear
inside or near the transition region; detections touching the artificial crop
edge can blink or receive new IDs. Even though detections remained, no one ID
retained enough complete OUTSIDE and INSIDE history to satisfy the conservative
counter. Zero events therefore does not show that ROI inference found zero
people; it shows why cropping and tracking must be separated and why a sole view
must cover both configured counting zones.

## v0.2 invariant

Every original source frame must cause exactly one update of one ByteTrack
instance. All view-local predictions are translated, clipped, excluded, and
fused in source coordinates before that update. Zones, lanes, counting,
diagnostics, and output rendering remain in source coordinates.
